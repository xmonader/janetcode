# Janetcode wild ideas

Twenty-five further ideas, generated by Claude, not taken from the research notes. Each one is aimed at a
fact janetcode has measured about itself:

- About 98% of wall time is the model generating.
- About 79% of output tokens are tool arguments.
- The remaining misses are hidden-test rules that the public tests do not reach.
- Exploration takes 43–54% of calls before the first edit.
- Memory captured the lesson in only 4 of 9 sessions that hit the trap.
- About 45% of broker runs are lost to infrastructure noise.
- Results vary 2–3× from one seed to the next.

A grep confirmed that janetcode does not already have each mechanism; where it has something close, the idea
says so. Ideas that duplicate the 13 in `Janetcode novel engineering ideas.md`, or janetcode's own rejected
experiments, are left out.

Each idea ends with a **Test:** line: the cheapest experiment that could falsify it, together with what to measure
and when to drop the idea. **Precedent:** names any outside work the idea borrows from.

## A. Hidden-test misses (the main remaining failure)

1. **Spec-coverage matrix.** Before the first edit, the harness pulls rules and worked examples out of the
   task text with a deterministic parser. It looks for numbered items, must/never/should clauses, and
   `input → output` pairs. It then cross-references their identifiers and literals against the public tests. It
   tells the model which rules have no public test, for example: "R3 and R5 are not covered by any public test;
   hidden tests probably check them." This targets the failure that is left, rather than asking for
   blanket diligence. The parser runs with no model call.
   **Test:** replay the effbench tasks offline. **Measure:** whether the hidden-test failures in r8–r13 fall on rules
   the matrix flags as uncovered. **Drop** if fewer than 60% do.

2. **Example harvesting.** Worked examples in the task text (`f(3) == 9`, sample CLI input and output) are
   compiled into executable probes. The harness runs them at the gate and freezes them, which feeds the probe
   ledger (idea 1 of the earlier report) without the model having to write any probes.
   **Test:** count how many effbench and held-out tasks contain extractable examples, and how many hidden
   failures one of those examples would have caught.

3. **Clean-room blind tester.** A cheap model gets **only the spec**, never the implementation, and writes
   hidden-test-style checks. The implementer never sees these checks; it is only told which rules failed. The
   separation is the point. The spec review reads the code and shares the implementer's blind spots, whereas
   hiding tests is what drove cheating to near zero in ImpossibleBench. The cost is one small-context call per
   run. It is not the rejected "spec review writes check scripts", because there the same model wrote the checks
   with the code in view, and that cost about 150 seconds per run.
   **Test:** held-out 8×4, on versus off. **Drop** if there is no gain in passes.

4. **Differential fuzzing for refactors.** When the task says the change keeps behaviour the same (refactor,
   optimise, clean up), the harness writes a Go fuzz harness. The harness calls each changed exported function
   in both the pre-edit package (copied from the snapshot under an alias import path) and the new one. It
   compares outputs for N seconds and reports the first input where they diverge. This turns "no behaviour
   change" from a claim into a fact.
   **Precedent:** differential testing in general. Generating the harness automatically from an agent's own
   diff is new here.
   **Test:** seed 5 refactor tasks with a subtle behaviour change and count how many it catches.

5. **Checks on numeric claims.** Any number in the final message ("40% faster", "allocations halved",
   "coverage 85%") must trace back to a measurement command in the event log. Speed claims additionally need a
   before-and-after run with `benchstat`-style significance. Unsupported numbers get rewritten as unverified,
   in the same way `verdict.go` already handles claims that tests pass.
   **Test:** collect the numeric claims in past sessions and measure what share have no measurement behind them.

6. **Flake quarantine.** When a test goes red, the harness re-runs it once on the pre-edit tree and once on the
   new tree. If either result flips between runs, it tells the model the test is non-deterministic, so the model
   does not "fix" noise. The gate already has a flaky verdict, but only inside the optional Jev triage; this
   version is deterministic and needs no model.
   **Test:** count the red runs in past sessions that were followed by edits to unrelated code.

## B. Wall time and output tokens

7. **Pattern induction for repetitive edits.** After the model makes two structurally similar edits, such as
   the same signature change or a renamed call with the same new argument, the harness infers the
   transformation in the style of PROSE program synthesis by example. It finds the remaining matching sites
   with tree-sitter and offers to apply the rest in one step: "N more sites match; apply all?" Each repetitive
   site the model does not have to write out saves output tokens and a round trip.
   **Precedent:** IntelliCode suggestions and Microsoft PROSE. Using it inside an agent loop is new.
   **Test:** offline, count runs with three or more structurally similar hunks. **Drop** if under 10%.

8. **Symbol pre-resolution for the first message.** The identifiers and paths named in the task are resolved
   with LSP or grep, and their definitions and covering tests are inlined into the first message under a byte
   budget. Inlining the whole repository already gave −41% calls on small repos; this extends the effect to large
   repos, where exploration takes 43–54% of calls.
   **Test:** the 58-file repository case. **Measure:** calls before the first edit. **Drop** if the drop is under 20%.

9. **Speculation during the user's think time (interactive).** While the user is reading a reply, janetcode
   runs the predicted next step in a shadow worktree on the cheap model. This is only done when there is a
   single clear follow-up and the cost cap allows it. If the user then sends that step, the result is
   ready immediately. Humans are the slowest part of the loop, and nobody uses their idle time.
   **Test:** offline, measure how often the follow-up suggestion matches the user's actual next prompt. **Drop**
   if under 40%.

10. **Request hedging and stream resume.** If the first token has not arrived by the p95 time-to-first-token for
    that provider, a duplicate request is sent to a second key or route, and whichever answers first wins. When a
    stream breaks mid-reply, janetcode asks the provider to continue from the partial assistant text instead of
    regenerating the whole reply, on providers that support continuing a prefilled reply (Anthropic, DeepSeek). This
    targets the roughly 45% of broker runs lost to infrastructure noise.
    **Precedent:** hedged requests ("The Tail at Scale"). No coding agent is known to resume an interrupted reply.
    **Test:** replay the broker failure log and count the runs that would have been rescued.

11. **Cross-session prefix kernels.** All sessions in a repository start from a byte-identical prefix:
    system prompt, tool list, and a repo-map snapshot keyed by the commit. The second session of the day then
    gets cache hits from the first call. DeepSeek prices a cache hit at about 2% of a miss.
    **Test:** start N sessions in sequence on the same commit. **Measure:** the cache-hit rate on the first call.

12. **Price-aware scheduler for headless work.** Benchmarks, `--cron` jobs and batch evals are queued into
    provider off-peak windows (DeepSeek: 50% off) with a deadline, so the discount comes with no change in
    quality.
    **Test:** take the cost of r13 and recompute it at off-peak prices.

## C. Memory as executable facts, not prose

13. **Executable memory.** Every bug an agent fixes leaves a frozen regression probe in a ledger stored with
    the repository, under `refs/janetcode/probes`. Later sessions replay these probes at the gate. A probe cannot
    carry injected instructions, which is the problem with poisoned memory, and capturing one does not depend on
    the model choosing to remember, which is why prose memory caught only 4 of 9 lessons. This gives memory that
    acts mechanically.
    **Test:** the "warm session" memory benchmark, run with probes instead of prose memory.

14. **Error-signature to fix cache.** When a session hits an error and then resolves it, janetcode stores the
    normalised error signature together with the fix diff pattern. If the same signature appears again in this
    repository, the fix that worked last time is attached to the error output, with no model call to retrieve it.
    **Test:** count how often error signatures recur across past sessions in the same repository.

15. **Agent blame on reads.** When the model reads lines that an earlier agent turn wrote with a recorded
    intent, the read result carries a one-line note, for example: "L40–52 was added on 2026-10-01 to fix X, and
    test Y guards it." This stops agents undoing deliberate fixes, which is a common way agents re-break code. It
    builds on the provenance git notes janetcode already writes.
    **Test:** seed tasks where the obvious edit reverts an earlier fix, and measure the revert rate with and
    without the note.

## D. Evaluation and noise (measurement is the binding constraint)

16. **A/B tests that branch mid-run.** Use `whatif` to replay a recorded run's first K replies exactly. Run
    both arms live only from step K. Both arms then share an identical history, which removes most of the
    variance caused by the first replies. This is especially useful for harness changes that only matter late in
    a run, such as gates, compaction and spec review.
    **Test:** compare the variance of paired branched runs with that of independent runs on one task.

17. **Sequential testing for evals.** Use always-valid p-values (mSPRT) in `internal/eval`, so an A/B stops
    as soon as the evidence is decisive. Use the same seeds and workspaces in both arms. Keep a separate count
    for broker-dropped runs instead of quietly discarding them. Every idea on the list is held back by eval
    cost, so cheaper evals speed all of them up.
    **Test:** re-analyse past A/Bs and measure how many runs each would have needed.

18. **Behavioural model fingerprint.** At the start of a session, send a few cheap canary prompts with known
    answers to check which model is actually serving. Compare their output style and logprobs with a stored
    fingerprint. This catches silent model swaps and quantisation changes on brokers. The broker did once
    serve Kimi under every model name and invalidated a result; the current check confirms the model name only,
    not the behaviour.
    **Test:** record fingerprints for 3 models and measure how reliably a swap is detected.

## E. Reviewing, scope and steering

19. **Scope contracts.** The expected blast radius is inferred from the task: files it mentions, their impact
    closure, and their tests. Edits outside it need a one-line justification that is recorded in provenance.
    A headless run reports scope creep as a metric.
    **Test:** measure what share of r13 diffs touch files outside the inferred scope, and whether those edits are
    linked to failures.

20. **Failure dossier.** When a headless run fails, it writes a structured hand-off for a human: the smallest
    reproduction, the hypotheses it tried with the evidence that ruled each out, the last red output, and a
    `whatif` pointer to the best state reached. This turns a failed run into useful work instead of wasted cost.
    **Test:** whether a human or a second run fixes the issue faster when given the dossier than without it.

21. **Live plan file for steering.** The plan lives in `.janetcode/plan.md`. The user edits it in their own
    editor while the agent runs, and the harness diffs it between steps and injects only the change. This gives
    steering without interrupting the run.
    **Test:** a user study, or scripted plan edits mid-run, measuring whether the change is followed.

22. **Turn-level bisect.** `janetcode why-broke <test>` runs `git bisect` over agent *turns* rather than
    commits. It rebuilds each turn's tree from snapshots or `whatif`, so it can point inside a single squashed
    commit. It then shows the intent of the turn responsible.
    **Test:** seed a regression inside a multi-turn session and confirm it is located correctly.

23. **Sessions as git refs.** The transcript, evidence and probes are stored under
    `refs/janetcode/sessions/<id>`, so they can be pushed with the branch. A reviewer can then open the session
    behind a pull request and re-run its evidence, together with idea 11 of the earlier report.
    **Test:** product only; check that the size of each ref stays under 1 MB per session.

## F. Safety

24. **Auto-approval from observed purity.** Each bash command runs under a side-effect monitor: Landlock
    audit or strace on Linux, and the sandbox's own write log. A command that is seen to be read-only across
    N runs in this repository is promoted to auto-approve, which lowers approval fatigue without trusting the
    classifier's guess.
    **Test:** measure approval prompts per interactive session with and without it.

25. **Dependency-confusion tripwire at edit time.** When the model adds an import or dependency, check the
    name for typosquatting against the module cache and the dependencies already in use, using edit distance and
    homoglyph checks. This works offline and catches confusable names before any network lookup. It complements
    the registry gate in idea 6 of the earlier report.
    **Test:** take known typosquat lists, seed the mistakes, and measure the detection rate.

## Where to start

The four ideas with the best expected value per unit of effort:

- **1, spec-coverage matrix:** aimed straight at the main remaining failure, and fully deterministic.
- **10, hedging and stream resume:** aimed at the 45% of runs lost to the broker.
- **16, branched A/B tests:** makes every later experiment cheaper.
- **7, pattern induction:** aimed at the 79% of output tokens that are tool arguments.

**13, executable memory** is the boldest idea and the one most specific to janetcode.
