Permissions and safety

Permission prompt y a r n c

Before janetcode edits a file or runs a command, it stops and shows the diff or the exact command. When it helps: nothing has approved this shape of command yet this session.

  allow bash go test ./internal/...
y allow once
a always for bash this session
r save rule bash(go test ./internal/...)
n deny (and say why)
c cancel the turn

Why it matters — the five keys are different scopes, not five ways to say yes or no; picking the wrong one is how a session either nags all afternoon or runs with the brakes off.

More detail

n asks for a reason first — typed text goes back to the model as guidance; empty input or esc sends a plain refusal. c denies this call and stops the whole turn, not just the one prompt.

Rules live under "permissions" in the config file as allow/deny lists. A project's own .janetcode/permissions.json needs a one-time /permissions trust before its allow rules apply (its deny rules apply immediately). A few destructive-looking commands (recursive deletes, force pushes, sudo, piping a download into a shell) are flagged even when a rule would allow them, and anything touching janetcode's own settings always asks, in every mode. More →

Learned permissions /permissions

A private tally of how you've answered past prompts offers to save a rule once a shape is approved three times running. When it helps: you've said yes to bash(go test *) four times today and are tired of it.

$ /permissions
approved often, not saved:
  /permissions allow bash(go test *)
  (approved 4×, never refused)

Why it matters — it counts rather than guesses, and one refusal, ever, takes a shape off the list for good. Nothing saves until you type the command or press r.

Modes shift+tab

One dial cycles four levels of how much janetcode asks before it acts: ask, plan, auto, yolo. When it helps: handing over work you already trust, without babysitting every edit.

$ shift+tab (×3)
PLAN   reads only · writes a plan
AUTO   edits and known-safe reads run
YOLO   tools run without asking

Why it matters — the status line says in plain words what the mode actually does, so the four read as one dial, not unrelated settings.

More detail

/plan <request> jumps straight into plan mode with a request queued; /auto and /yolo toggle those two directly without cycling. /readonly (or --readonly) is not on this cycle — it refuses every mutating call for the rest of the session. Plan mode's plan is a numbered list you approve with /plan approve, after which each step runs as an ordinary, verified turn.

Remote workspace /ssh /docker

Retargets the file-reading, file-editing and shell tools onto another machine or a running container — the session, memory and undo history all stay local. When it helps: the code you want changed lives on a build box you reach over ssh, and you'd rather not copy it locally first.

$ /ssh build@10.0.4.12:/srv/app
workspace build@10.0.4.12:/srv/app
· file tools and bash run there

Why it matters — /ssh needs a working key or ssh-agent, it will not prompt for a password. /docker container[:/path] does the same for a running container, and off on either returns to the local directory.

Sandboxing /sandbox

Wraps the shell commands janetcode runs in Docker (or sandbox-exec on macOS) so a command can't reach the rest of your machine — file tools still act on the real workspace directly, only the shell is contained. When it helps: the model needs to run arbitrary commands — installing a package, a build script it wrote — without them reaching anything outside the project.

$ /sandbox on
sandbox on · bash runs in docker
  (janetcode-sandbox)

Why it matters — this is independent of where the tools point: /sandbox only isolates the shell, and it's off by default.

Hooks .janetcode/hooks.json

Shell commands run at fixed points in the loop, whose output can block a call or add a note. When it helps: check every edit with gofmt -l automatically.

"post_tool": [{
  "match": "write_file|edit_file",
  "command": "gofmt -l . | sed
    's/^/unformatted: /'"
}]
$ /hooks trust
trusted .janetcode/hooks.json · ...
… unformatted: parse.go

Why it matters — a project hook can't reach the network, since trusting a clone's hooks is a decision about that clone, not a blank check.

More detail

Your own hooks, listed under "hooks" in the config file, run unrestricted. A hook exits 2 to block a call (or a stop hook to send the model back to work), and can print JSON to rewrite input or attach a note, or plain text as a note. Config reference →

Sessions and history

Sessions: resume and fork --resume /fork

Every conversation saves automatically; pick it back up, branch it, or search across every session you've run. When it helps: try a second, riskier approach without losing the first.

$ /resume 2
$ /fork try-the-generic-version
20260911-153001-4f2a  42 msgs
claude-opus-5 · rename Config to Settings

Why it matters — a fork never mutates the original, only reads it; /resume then lists both, the copy carrying a fork_of link back to it.

More detail

janetcode --sessions lists every session for this directory; --continue resumes the newest one. /history <words> searches every saved session in every directory for a match. More →

Compaction and the archive /context

The old part of a long session is condensed into a short working record instead of resent in full. When it helps: you'd rather see what's filling the context than watch it fill.

$ /context
context ~92k tokens
compaction at 80k (115%) · 48 messages
largest tool results:
  18.2k  bash go test ./... (message 31)

Why it matters — nothing compacted is thrown away, just trimmed to a placeholder like bash "go test ./..." → exit 1; last line: FAIL pkg; expand_output recovers the exact text instead of a guess.

More detail

Compaction happens automatically once the conversation passes 80,000 tokens by default — deliberately far below any model's real window, since a smaller working context is cheaper, caches better, and is attended to more carefully — or on demand with /compact.

Memory /remember

Facts and preferences kept across sessions as small markdown files, recalled in full only when a request clearly overlaps one. When it helps: you've told the model twice this week that this project always runs make check before a commit, and want it to just know.

$ /remember always run `make check`
  before considering a change done
remembered: always run `make check`…

Why it matters — a value that looks like a credential is refused outright, since memory is written to disk and read back into every later prompt — the last place a secret belongs.

Path-scoped rules /rules

A markdown file with path globs in its frontmatter, sent to the model only once a tool call actually touches a matching path. When it helps: a rule that only matters for one corner of a large repository (“migrations are append-only”) would be wasted context on every other request.

$ /rules
migrations  waiting
  db/migrations/**,*.sql
migrations are append-only

Why it matters — unlike project instructions, sent on every request whether relevant or not, a migrations-only rule costs nothing in every turn that isn't touching migrations.

Skills /skills

A markdown file of instructions for one kind of task, attached automatically when a request matches it, or run directly as a command. When it helps: a house procedure (“how we cut a release”) that should be available without pasting it into every request.

$ /skills
release-checklist   Ship a release
  to production  (project)

Why it matters — memory, skills and rules are three different ways to avoid re-explaining something: memory is a recalled fact, a skill is a whole procedure read on request or by match, a rule enters only once a matching path is touched.

Undo and provenance

Undo a turn /undo

Reverts a whole turn's file changes, including a shell command's side effects inside a git repository. When it helps: you want to see what a turn did before trusting it's gone.

$ /undo preview
remove internal/export/csv.go
$ /undo
↲ removed internal/export/csv.go
verified: go test ./... (1.4s)

Why it matters — preview costs nothing, so you can check before committing to it. It goes back up to 30 turns, and /redo reapplies a reverted undo.

More detail

Outside git, only edits made through the file-editing tools can be reverted — a shell command's own side effects are not tracked. /undo N reverts one recorded change on its own, leaving later changes to the same file in place. More →

Undo by description /undo about

Picks out changes matching a plain-language description, and warns when undoing one breaks another. When it helps: a session did two unrelated things and you only want one gone.

$ /undo about the rename
[undo ] #3  config.go
  · rename Config to Settings
[keep ] #4  log.go
  · fix duplicate log line
warning: #5 uses Settings —
  undoing #3 would likely not build
$ /undo apply --force
↲ reverted 1 hunk(s) of config.go

Why it matters — the coupling check is a deterministic pass over the diffs, not a model's guess; --force is the deliberate override, not the default.

Change provenance /changes /blame

Groups edits by turn with the model's stated intent, and attributes each line of a file to the change that wrote it. When it helps: a file looks wrong and you want to know which turn wrote which line, and why.

$ /changes
turn 3 · rename Config to Settings
  · config.go +12 -12
$ /blame internal/config/config.go
#3  12 │ type Settings struct {

Why it matters — a session-scoped cousin of git blame that also knows why a line was written, not just when.

Proof in the commit /proof

Attaches the provenance record to the git commit itself — which session and turn wrote it, and what the harness observed. When it helps: code review asks why a line looks this way, and whether it was tested.

$ /proof
✓ turn 3: verified: 1 file(s) edited
  and tests ran and passed afterwards
parse.go · #3 edit_file +14 -3
  · handle trailing commas

Why it matters — it travels with the commit, not the session file, since git doesn't push or fetch notes on its own.

More detail

Attached automatically when a bash call that looks like git commit succeeds. /proof push/fetch move it to and from a remote, since git doesn't do that on its own; an --amend or rebase carries the note onto the new commit. Turn it off with "proof_notes": false. More →

Verification and quality

Verification gates and verdicts /verify set

A gate is the command that defines “done”; a verdict is janetcode's own judgment about what a turn actually demonstrated. When it helps: you want “tests pass” to mean something, not just a sentence the model wrote.

$ /verify set go test ./...
set: go test ./...
✓ verified: 2 file(s) edited
  and tests ran and passed afterwards
⚠ unverified: 2 file(s) edited
  and nothing was run against them
✗ check failed: 2 file(s) edited
  and a check came back red

Why it matters — a model that writes “tests pass” without running anything still gets ⚠ unverified, not ✓.

More detail

The seven verdicts are verified, self-checked (tests passed, but were edited this turn too), not demonstrated, unverified, check failed, vacuous (a check exited clean having found no tests to run), and tests written. A project can go further with "mutate": "<test command>": once checks pass, janetcode flips one operator at a time in the lines the turn changed and re-runs the tests against each mutant in a throwaway worktree, capped at twelve mutants per turn. More →

Acceptance tests /accept

A test-first mode: the model writes failing tests for a request, and once you approve them, they're locked. When it helps: you want to agree the tests before any implementation exists.

$ /accept approve
accept: locked  export_test.go
… export_test.go is a locked
  acceptance test; the edit was reverted.

Why it matters — each locked file is hashed at lock time and re-checked after every mutating call, so a green from editing the test back to passing was never a real green.

More detail

/accept unlock lifts the lock when a test turns out to be wrong itself; /accept command <cmd> corrects the verify command if janetcode's guess was wrong.

The reach of an edit impact line

The approval prompt names what an edit reaches: the symbols it touches, how many places reference them, and which tests cover them. When it helps: is this one-line-looking change touching something used in fourteen places?

  allow edit_file parse/parse.go
  changes Parse (func)
  · used 14 times in 6 files
  tests: parse_test.go
  · checks: go test ./...

Why it matters — the count comes from a running language server or the repository's symbol index (marked may miss some uses), computed in well under a second so approving never feels slower.

Diagnostics from language servers /lsp

A running language server's diagnostics ride along on every edit result, so a type error shows up in the step that caused it. When it helps: Go, Python, TypeScript, Rust or C — catching a broken reference before the next build.

$ /lsp
gopls: running (pid 48213, 6 files open)
parse.go:14:9: cannot use "no" (untyped
  string constant) as int (compile)

Why it matters — the same background process your editor already uses for autocomplete and inline errors.

Trajectory critic automatic

Watches the shape of a turn: a repeated call or a failing edit-run-fail cycle gets flagged and ends the turn. When it helps: a stuck turn would otherwise burn calls until a model-call cap ends it.

Automatic; --eval-off critic,plan disables it for an eval run.

Why it matters — an identical call repeated three times gets a note, five ends the turn; a failing two-to-four-step cycle is named after three rounds and ends after six.

More detail

It also checks a plan against the repository before tools run — a file or symbol named in the model's own text that doesn't exist gets flagged. It can learn from eval history too: as of the current bundled data (35 runs, 3 failures), there haven't been enough failing runs to show it beats guessing the majority outcome, so it isn't shipped switched on by that path yet.

Automation and replay

Recipes /recipe save /recipe run

Turns a turn's tool calls into a JSON file that replays with no model call and no tokens spent. When it helps: replay a fixed lint complaint instead of paying a model to redo it.

$ /recipe save fix-lint-header --turn 6
.janetcode/recipes/fix-lint-header.json
  run with /recipe run fix-lint-header
$ /recipe run fix-lint-header
recipe fix-lint-header: replaying 5 steps
✓ verified: 1 file(s) edited
  and tests ran and passed afterwards

Why it matters — the moment a step's target no longer matches what was recorded, it refuses to overwrite blind and hands the rest to the model.

More detail

e.g. header.go did not exist when this recipe was recorded, but it exists now with different content; refusing to overwrite it rather than guess. Saved recipes live in .janetcode/recipes/ and are meant to be committed, the same as custom commands and evals.

Evals from a session /eval keep

Writes a regression test from a real session, not one typed from memory later. When it helps: a bug got fixed this session and you want it to stay fixed.

$ /eval keep fix-trailing-comma
.janetcode/evals/fix-trailing-comma.json
  · 2 prompts
$ janetcode --eval .janetcode/evals
PASS fix-trailing-comma  4.1s  3 tools
  $0.0009 · 1/1 passed

Why it matters — it replays against the state the bug actually appeared in; if the check already passes there, /eval keep says so rather than keeping a task that can never fail.

More detail

--eval-runs 3 repeats each task and reports a pass rate with a statistical interval, and --eval-compare pairs two result files and reports the delta — the project's own report found a 21% spread between three identical runs of one task set, which is why this exists rather than trusting a single run. More →

What-if replay --what-if

Replays turns before a chosen point for free, then runs the rest live against one change — a different model, a reworded prompt — inside a throwaway worktree. When it helps: “would a cheaper model have solved this?” without redoing the session by hand.

$ janetcode --what-if 20260911-153001-4f2a \
  --from-turn 4 --model claude-opus-5
diverges at turn 4: edit_file parse.go
  (recorded) vs token.go (this run)
turn 4  recorded: ⚠ unverified
  this run: ✓ verified

Why it matters — it answers “what if” against exactly what happened, and refuses up front, before spending anything, when there's no recorded starting state to replay from.

Background jobs ctrl+g

Moves a running shell command to the background so the turn continues, and tells the model the moment it finishes. When it helps: a foreground build is taking longer than expected.

$ ctrl+g
moved to background as job 1
  · /jobs shows it
job 1 running for 42s (pid 88213):
  go build ./...
⚙ job 1 finished with exit 0

Why it matters — moving a command to the background is your call about something already running, not the model's; the job just stops holding the turn open.

Custom commands /<name>

A prompt template stored as a file, submitted as a slash command with your arguments substituted in. When it helps: a request you type often, worded the same way every time.

Add .janetcode/commands/<name>.md; run it as /<name> args, with $ARGUMENTS replaced in the template.

Why it matters — one file instead of retyping the same wording into the prompt every time.

Step routing route_cheap experimental

Sends a turn's mechanical steps — reading a file, re-running a passed check — to a second, cheaper model; planning and edits stay on the main one. When it helps: nothing yet, by design, until an eval shows a real saving.

"route_cheap": "<model>"; empty (default) is off. Config reference →

Why it matters — the policy is a short list of fixed rules, not anything learned, and must be demonstrated per project with an eval comparison first.

Delegation

Subagents /agents /review

A bounded second conversation that does one job in its own context; only the final report comes back. When it helps: a second, independent pass over the diff before committing.

$ /review
started review · two subagents
  · /agents watches them
review bugs   done   found:
  parse.go:88 ignores the error
  from Close()
review tests  done   found:
  no test covers the empty-input
  case in Parse

Why it matters — the two subagents get separate briefs over the same git diff HEAD, so you get two independent readings instead of one pass trying to do both.

More detail

/agents new <brief> starts a plain read-only subagent directly; /agents fork <brief> starts one that inherits this whole conversation's history. A subagent with edit: true gets the full tool set inside a worktree — a second, temporary checkout on its own branch — and returns a patch for you to review rather than changing your real tree. More →

Custom agents .janetcode/agents/*.md

A markdown profile setting a subagent's instructions, allowed tools and model, picked by name. When it helps: a subagent that only reviews, never edits or reaches the network.

.janetcode/agents/reviewer.md:
---
description: Reviews a change
  for correctness
tools: read_file, grep, glob
disallowed_tools: fetch_url, web_search
---
review bugs   done   found:
  parse.go:88 ignores the error
  from Close()

Why it matters — disallowed_tools applies after the tools allowlist, so nothing can hand a forbidden tool back by naming it.

Extending janetcode

MCP servers /mcp trust

MCP is a standard way for a program to offer tools to an agent; janetcode's built-in tools gain whatever a connected server offers. When it helps: reaching a real browser, a company's internal API, a database.

$ /mcp trust
trusted .mcp.json · starting its servers

Why it matters — a project's .mcp.json can run arbitrary commands on your machine, so it's shown at startup but stays inert until you explicitly trust it once; editing the file asks again.

More detail

A server with more than six tools has them registered deferred: schemas are sent only when the model searches for one by keyword, so a browsing session pays for its many tools and a plain coding session does not. Image content from a server is replaced with a placeholder, and the model works from the accessibility tree instead of pixels. More →

Repository map repo_map

A ranked map of which files and symbols matter for a request — links are “file A uses a symbol file B defines,” ranked the way a search engine ranks pages. When it helps: a sense of the codebase's shape without reading every file first.

Why it matters — by default it parses Go with the standard parser and everything else with regular expressions; make build-treesitter compiles in real grammars for more languages, at the cost of a C toolchain.

Interfaces and cost

Headless and scripting janetcode -p

Runs one prompt to completion, no interactive terminal: text on stdout, tool activity on stderr. When it helps: a CI script runs one prompt and parses the result.

$ janetcode -p "uppercase out.txt" \
  --output-format json
{
  "result": "out.txt now holds the
    uppercased text.",
  "is_error": false,
  …
  "verdict": "tests pass"
}

Why it matters — verdict comes from what the harness watched, not the model's claim, so a script checking it gets an honest answer.

More detail

Without --yolo and with no terminal to ask, a mutating tool call is simply denied rather than left hanging. --until "<cmd>" keeps a run going until a command exits 0, up to five rounds. More →

The web UI --web

The same session in a browser instead of the terminal, for approving commands and reading a long diff in a tab. When it helps: you'd rather click through permission prompts than use the terminal.

$ janetcode --web
janetcode 0.9.0 serving
  http://127.0.0.1:8787
  (claude-opus-5 in ~/project)

Why it matters — it's loopback-only by default, and bound anywhere else it asks for the access token in the URL it printed, so a port someone else can reach does not hand them your shell.

Editor integration --acp

Speaks the Agent Client Protocol on stdio, so an ACP editor can drive janetcode directly instead of through a terminal. When it helps: your editor wants to drive janetcode itself — sessions, streamed replies and permission prompts as protocol messages.

$ janetcode --acp
{
  "jsonrpc": "2.0",
  "method": "session/update",
  "params": {
    "sessionId": "sess-1",
    "update": {
      "sessionUpdate":
        "agent_message_chunk",
      "content": {
        "type": "text",
        "text": "Reading parse.go..."
      }
    }
  }
}

Why it matters — ACP is not a chat UI at all — it's the same tool-call and permission machinery, addressed by an editor instead of a terminal.

Cost control /budget

A running total of tokens and cost, with an optional hard ceiling that stops the session once reached. When it helps: stop on its own before spending more than fifty cents.

$ /budget 0.50
cost budget $0.50 · the session
  stops when it crosses that
$ /usage
in 12.4k · out 3.1k
  · cost $0.0187
  (reported by the provider)

Why it matters — the ceiling is checked after every model call, so a long single turn can still overshoot it by one call's worth. --max-cost 0.50 does the same for a headless run, and exits with code 55 if crossed.

Themes /theme

A named colour palette for the terminal interface — eighteen are built in, from a historical default to Solarized, Nord, Dracula, Gruvbox and Catppuccin. When it helps: the default colours are hard to read on your terminal or background.

/theme opens a live, searchable list; /theme <name> switches directly.

Why it matters — you can also define your own with fourteen named colour roles in the config file.

Hints automatic

One-time, faint notices about a feature you appear not to know about, shown at the exact moment it would have helped. When it helps: you're new to janetcode, or have never needed a particular corner of it.

On by default; /hints off silences them for the session.

Why it matters — each hint fires at most once, ever, and never for a feature you already use.
