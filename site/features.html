Safety and control

Permission rules and modes

What it is
Before janetcode edits a file or runs a shell command, it asks you first — showing the diff or the exact command — unless you have told it not to. Four modes control how much it asks: ask (everything asks, the default), plan (read-only until you approve a plan), auto (in-workspace edits and known-safe reads run, other commands still ask) and yolo (nothing asks).
When it helps
You are letting an agent touch a real project and want to see every change before it lands, but do not want to re-approve “run go test ./...” for the fortieth time in one session.
How to use it
shift+tab cycles the four modes; --yolo, --auto and --auto-edits set one for a run. At a prompt, y allows once, a allows that tool for the session, n denies with a reason, and r saves a permission rule such as bash(go test *) so the same shape of call never asks again, in any session.

Rules live under "permissions" in the config file, as allow and deny lists; a denied rule always wins. /permissions lists and adds rules. A project can ship its own .janetcode/permissions.json — its deny rules apply immediately, but its allow rules need a one-time /permissions trust, since a cloned repository should not be able to silently widen what it is allowed to do on your machine. A few destructive-looking commands (recursive deletes, force pushes, sudo, piping a download into a shell) are flagged even when a rule would otherwise allow them, and anything that would touch janetcode's own settings — the config file, .mcp.json, everything under .janetcode/ — always asks, in every mode, because a model that can silently widen its own permissions and then use them is the one thing worth always showing a human.

janetcode separately keeps a private, per-project record of how you answered past prompts. It never saves a rule for you; once a call's shape has been approved three times running with no refusal, the prompt notes that next to the rule r would save, and /permissions lists it under “approved often, not saved”.

Sandboxing

What it is
Wraps the shell commands janetcode runs in Docker (or sandbox-exec on macOS), so a command runs isolated from the rest of your machine. File tools (reading and editing) still act on the real workspace directly; only the shell is contained.
When it helps
You want the model to be able to run arbitrary commands — installing a package, running a build script it wrote — without those commands reaching anything outside the project.
How to use it
--sandbox on the command line, or /sandbox on mid-session; off by default.

Plan mode and read-only mode

What it is
Plan mode restricts the model to read-only tools while it explores the code and writes a numbered plan; nothing changes until you approve it, after which each step of the plan runs as an ordinary, verified turn. Read-only mode is the same restriction with no plan attached: the model can inspect and answer, but change nothing, for the rest of the session.
When it helps
A change big enough that you want to read the plan before any file is touched; or you want the model's read of a codebase without any risk of it editing something.
How to use it
/plan <request>, then /plan approve to execute it or /plan off to leave without executing; /readonly or the --readonly flag for the plain restriction.

Remote workspaces

What it is
Retargets the file-reading, file-editing and shell tools onto another machine or a running container, without restarting the session. The session itself, memory and undo history all stay local; only what the model reads, writes and runs moves.
When it helps
The code you want worked on lives on a remote server or inside a running container, and you would rather not copy it locally first.
How to use it
/ssh user@host[:/path] (needs a working key or ssh-agent; it will not prompt for a password) and /docker container[:/path]; either one with off returns to the local directory.

Sessions and history

Sessions: resume, fork, compaction, archive

What it is
Every conversation is saved, append-only, as a local file. You can pick it back up later, branch it into a second attempt, or search across every session you have ever run in any directory. When a conversation grows large, the old part is compacted — condensed into a short working-memory record — instead of being resent in full on every request, and the archive (see below) keeps the full text on disk regardless.
When it helps
You want to stop mid-task and pick up tomorrow exactly where you left off, try two different approaches from the same starting point, or find which past session dealt with a bug you now vaguely remember.
How to use it
--continue resumes the newest session for this directory, --resume <id> a named one, --sessions lists them; inside a session, /resume, /fork [stay] [title], /title <text> and /history <words> do the same and more.

Compaction happens automatically once the conversation passes a token threshold (80,000 by default — deliberately far below any model's real window, since a smaller working context is cheaper, caches better, and is attended to more carefully), or on demand with /compact. The summary is not free-form prose: it is a typed record — files edited with a hash of their current content, files read, commands run with their exit codes, open questions, next steps — that the model updates rather than rewrites from scratch each time, so it does not drift.

Nothing compaction removes is actually thrown away. The full text of every long tool result and of the conversation compaction replaces goes to a local archive; the expand_output tool searches it by words, by an exact file-and-line reference, or by regular expression. Measured by forcing compaction and then asking for facts that had been condensed away: 0 of 16 were recalled with no archive to check, 9 of 20 (45%) with it, and every correct answer was traced back to something actually fetched from the archive rather than guessed (docs/benchmarks/compaction/FACTS.md).

Undo and change provenance

What it is
Every file change a turn makes is recorded with the model's own stated reason for it — a record janetcode calls provenance — so the session's work can be read back and reverted one decision at a time, not just one whole turn at a time.
When it helps
The model changed the wrong thing and you want just that back; or a file looks wrong days later and you want to know which turn, and why, wrote the line in question.
How to use it
/undo reverts the last changing turn entirely; /changes lists recorded changes by turn and intent, and /changes N shows one change's hunks; /blame <path> attributes each line of a file to the change that wrote it; /undo N reverts one recorded change on its own, leaving later changes to the same file in place.

Inside a git repository, a whole-turn /undo uses a hidden snapshot taken before the turn's first change (through a temporary index, so your own HEAD, index and branches are never touched), so it also reverts anything a shell command changed or deleted — not just file-tool edits. Outside git, only edits made through the file-editing tools can be reverted. It can go back up to 30 turns, and still works after resuming a session. /redo reapplies what the last undo reverted, until the next change makes that ambiguous.

/undo about <description> is the finer instrument: it previews which of the session's recorded changes match a plain-language description (“the logging changes but keep the rename”), listed as undo, keep or mixed (an edit that partly matches), and a deterministic check simulates the revert to warn when keeping one change while undoing another would leave code referring to something that no longer exists. Nothing is touched until /undo apply, which reverts exactly that preview and reports whether the result still passes the project's checks.

Proof in the commit

What it is
Makes the provenance record above outlive the session by attaching it to a git commit: which session, which turn, and its stated intent wrote each of the commit's files, plus what the harness actually observed demonstrating the work (the turn's verdict — see below), not the model's own claim.
When it helps
Code review, or months later: “why is this line here, and what actually showed it worked?” answered from the commit itself rather than from a chat log nobody kept.
How to use it
Automatic: when a bash call that looks like git commit succeeds and HEAD moves, the note is attached without being asked. /proof [commit] prints it (attaching one first if there isn't one yet); /proof push [remote] and /proof fetch [remote] move notes to and from a remote, since git does not push or fetch notes on its own.

The note is stored as a git note under refs/notes/janetcode, local to the clone that made it until pushed. Two sessions that both touch one commit merge their notes rather than overwrite each other, and janetcode configures git so an --amend or a rebase carries the note onto the new commit instead of leaving it orphaned. Turn this off with "proof_notes": false in the config file.

Verification and quality

Verification gates and verdicts

What it is
A verification gate is a set of commands the project defines as what “done” means (a build, a test run); janetcode runs them after any turn that changed something and feeds a failure back to the model. A verdict is janetcode's own judgment, on top of that, about what a turn actually demonstrated — computed from what it watched run, not from the model's summary of what it did.
When it helps
You want “done, tests pass” to mean something, instead of trusting a sentence the model wrote about its own work.
How to use it
/verify set <cmd> or .janetcode/verify.json defines the gate; /verify alone runs it now. The verdict needs no setup — it appears under every turn that changed code, and --eval-off verdict turns it off for an eval run.

The seven verdicts are verified (tests ran and passed), self-checked (tests passed, but were edited this turn too), not demonstrated (something ran but proved nothing), unverified (nothing was run at all), check failed, vacuous (a check exited clean having found no tests to run), and tests written (an acceptance-test turn wrote tests that correctly fail, since the code does not exist yet). Full table and how it fits the turn loop: how it works.

A project can go further with "mutate": "<test command>": once the checks pass, janetcode flips one operator at a time in the lines the turn changed (== to !=, < to <=, and similar) and re-runs the tests against each mutant in a throwaway worktree (a second, temporary checkout of the repository). A mutant the tests do not catch means that line's behaviour is not actually pinned down by a test, whatever the test suite's pass/fail says. At most twelve mutants run per turn, so the cost is bounded.

Acceptance tests

What it is
A test-first mode: the model's only job is to write tests for a request that fail against the current code and would pass once the request is done. Once you approve them, they are locked — no tool call, from the model or from a script, can weaken or delete them — and their command becomes an extra gate for the rest of the session.
When it helps
You want to see and agree with the tests before any implementation exists, so the model cannot make a test pass by quietly rewriting it once the real fix turns out hard.
How to use it
/accept <request> to write tests, /diff <path> to review each one (they are new files, so the diff is the whole file), then /accept approve to lock them in.

While locked, an edit or a shell command that would touch a locked test file is refused up front; as a second line of defence, the exact content of each locked file is hashed at lock time and checked again after every mutating call, so even a command the up-front check missed gets the file restored immediately, with a notice. /accept unlock lifts the lock when a test turns out to be wrong itself; /accept command <cmd> corrects the verify command if janetcode's guess was wrong.

Diagnostics from language servers

What it is
A language server (LSP, for Language Server Protocol) is the background process your editor already uses for autocomplete, go-to-definition and inline errors. When one is installed for the file's language, every edit's result carries its diagnostics, so a type error shows up in the same step that caused it rather than at the next build.
When it helps
Go, Python, TypeScript, Rust or C code, where a language server (gopls, pyright, typescript-language-server, rust-analyzer, clangd) is on your PATH; catches a broken reference or a type mismatch immediately instead of after a full build.
How to use it
Automatic once the server is installed; /lsp shows server status, and the model has a diagnostics tool to re-check a file or list every known problem on demand.

The same connection also answers symbols queries — where a name is defined, every place it is used, its type, or everything a file declares — which is one call against the resolved program instead of a text search that cannot tell a declaration from a mention in a comment.

The reach of an edit

What it is
When you are asked to approve an edit to a file that already exists, the prompt adds an impact line naming what the change reaches: the symbols it touches, how many places reference each one, which test files already cover them, and which verification commands will run — for example, changes Parse (func) · 14 refs in 6 files · tests: parse_test.go · checks: go test ./....
When it helps
Deciding, at a glance, whether a one-line-looking change is actually touching something used in fourteen places before you approve it.
How to use it
Automatic, shown in the permission prompt itself; nothing to turn on.

The answer comes from the language server when one is available, and from the repository map otherwise (see below), marked (partial) when it had to fall back to the coarser count. It never delays the prompt beyond a fixed, short budget; whatever is not known in time is simply left out.

Trajectory critic

What it is
Watches the shape of a turn, not just its last call: an identical tool call repeated three times gets a note and five ends the turn; a two-to-four-step cycle that keeps failing (edit, run the failing test, edit again, fail again) is named after three rounds and ends the turn after six. It also checks a plan against the repository before tools run — a file or symbol named in the model's own text that does not actually exist gets flagged.
When it helps
Stops a stuck turn from burning tool calls and money on a loop that is not converging, rather than waiting for a model-call cap to end it.
How to use it
Automatic; --eval-off critic,plan disables the two halves for an eval run.

It can also learn: every eval run records a turn's shape (tool calls, errors, test runs, repeats) against pass or fail, and make eval-train fits a small model to that data. Once trained, it scores a live turn every five tool calls and, the first time the estimated chance of success drops under 35%, gives the model one note naming what is pulling the odds down. As of the current bundled data (35 runs, 3 failures) there have not been enough failing runs to show it beats simply guessing the majority outcome, so it is not shipped switched on by that path yet.

Automation and replay

Recipes: replay a turn for free

What it is
Turns a turn's tool calls — the files it read, the exact edits it made, the commands it ran — into a small JSON file that replays them later with no model call and no tokens spent, verifying at each step that the file still matches what was recorded before touching it.
When it helps
A repeatable job — bumping a version number in three files, a release checklist — that already worked once as a normal turn and does not need a model's judgement to do again.
How to use it
/recipe save <name> after a turn that worked; /recipe run <name> key=value to replay it, with parameters substituted; janetcode --recipe <name> runs one with no session open at all.

A recipe step never blindly replays a position: a text edit must still match the current file exactly once, and a step that creates a new file refuses to run if the path already exists with different content. If any step cannot be verified this way, replay stops without touching anything, and hands off to the model as an ordinary turn — the same fallback used when the project's own verification gate fails after a clean replay. Saved recipes live in .janetcode/recipes/ and are meant to be committed, the same as custom commands and evals.

Evals, and keeping a session as one

What it is
An eval here is a scripted task — a prompt, some setup files, and a shell check that must exit 0 — run against a model with a minimal, fixed toolset, so a harness change or a prompt change can be measured rather than eyeballed from a transcript. /eval keep writes one directly from a real session that already happened.
When it helps
A bug got fixed or a feature got built in a real session, and you want to make sure it stays fixed as the project and the harness change — a regression test written from what actually happened rather than typed by hand.
How to use it
/eval keep [name] [--check cmd] inside a session; janetcode --eval .janetcode/evals to run the kept tasks later; make eval for the project's bundled task set.

A kept task records the commit the session started from and a diff of anything left uncommitted at that point, so replaying it recreates the exact starting tree, not just the prompt. Because one run of a small task set is close to a coin flip, --eval-runs 3 repeats each task and reports a pass rate with a statistical interval, and --eval-compare pairs two result files and reports the delta — the project's own report found a 21% spread between three identical runs of one task set, which is the whole reason this exists rather than trusting a single run.

What-if: replaying a session with one thing changed

What it is
Answers “what would have happened if…” for a session that already ran: replays the turns before a chosen point for free from the recorded transcript, then runs the remaining turns live against one change — a different model, a disabled behaviour, an extra deny rule, or a reworded prompt — entirely inside a throwaway worktree, so your real project is never touched.
When it helps
“Would a cheaper model still have solved this?” or “would it have found the same fix if I'd phrased the request differently?” without redoing the whole session by hand.
How to use it
janetcode --what-if <session> --from-turn <n> [--model m] [--off names] [--prompt "text"].

The report at the end shows where the two runs first diverge, a verdict for each turn on each side, which files each side touched, a run of the project's own checks in the resulting worktree, and cost split into what the whole session would have cost against what this run actually spent new — the replayed part is free. It refuses up front, before spending anything, when the session has no recorded starting state to replay from.

Background jobs

What it is
A shell command started detached: it runs in its own process group with output going to a log file, and the turn continues immediately rather than waiting for it. When the job ends, the model is told before its next call.
When it helps
A dev server, a long build, or a slow test suite that should not hold the whole conversation open while it runs.
How to use it
The model starts one with bash's background: true; a command already running in the foreground can be moved there with ctrl+g. /jobs opens a live overlay to tail, kill, or write to one; the model has a matching job tool.

Hooks

What it is
Shell commands run at fixed points in the loop — before a tool call, after one, before compaction, when a turn ends — whose output can block the call, rewrite its input, or add a note to the conversation.
When it helps
Enforcing a house rule outside the model's judgement: block any bash call against a policy script, or run gofmt -l after every edit and surface the result.
How to use it
Your own hooks go under "hooks" in the config file and run unrestricted; a project's .janetcode/hooks.json needs a one-time /hooks trust and is held to tighter limits (capped timeout, no network access) since trusting a clone's hooks is a decision about that clone, not a blank check.

A hook exits 2 to block a call (or a stop hook to send the model back to work), prints JSON to rewrite input or attach a note, or prints plain text as a note; any other outcome, a crash, or a timeout is logged and ignored — hooks fail open, so a broken one cannot wedge a session.

Delegation

Subagents and teams

What it is
A subagent is a second, bounded conversation the main model starts with the task tool to do one job in its own context — explore a directory, fix one test, review a diff — on the same model or a different, perhaps cheaper one. Several can run in parallel, and only the final report comes back to the main conversation unless you open its own transcript.
When it helps
A side task that would otherwise fill the main conversation with reading it does not need to keep, or a job better suited to a cheaper model than the one steering the whole task.
How to use it
The model calls task on its own; /agents (or ctrl+t) opens a live overlay of subagents this session started, and /agents new <brief> starts one yourself.

task {"agent": "explore"} is a built-in, read-only subagent for wide reading with no editing tools at all; a subagent with edit: true instead gets the full tool set inside a worktree — a second, temporary checkout of the repository on its own branch — so it can edit and run commands without asking, and returns a patch for you to review rather than having changed your real tree. --worktree <branch> does the same for an entire session.

Custom agents

What it is
A named subagent profile — a markdown file that sets its own system-prompt text, an allowed tool list, and optionally a different model — that the model can pick by name.
When it helps
A recurring kind of subagent job (“strict reviewer, read-only”, “fixes one failing test in its own checkout”) worth defining once instead of describing in the prompt every time.
How to use it
Add .janetcode/agents/<name>.md with frontmatter (description, tools, model) and a body of instructions; /agents new <brief> starts the built-in general profile, /agents fork <brief> starts one that inherits the current conversation.

Extending janetcode

MCP servers

What it is
MCP (Model Context Protocol) is a standard way for a program to offer tools to an agent. janetcode is an MCP client: it can start a local server over stdio, or connect to a remote one over HTTP, and the server's tools become available to the model alongside the built-in ones.
When it helps
Reaching something janetcode has no built-in tool for — a real browser (Chrome's own devtools MCP server), a company's internal API, a database.
How to use it
List a server under "mcp_servers" in the config file to start it with every session, or ship a project .mcp.json that starts once you run /mcp trust. /mcp shows status and tools; /mcp auth <server> runs an OAuth login for a server that needs one.

A server with more than six tools has them registered deferred: their schemas are not sent with every request, only when the model searches for one by keyword, so a browsing session pays for its 29 tools and a plain coding session does not. Screenshots cannot quietly fill the context either — janetcode's tool interface is text-only, so image content from a server is replaced with a placeholder and the model works from the accessibility tree instead of pixels.

Skills

What it is
A markdown file of instructions for one kind of task, attached to the conversation automatically when a request clearly matches it, or run directly as a command.
When it helps
A house procedure (“how we cut a release”, “the steps for adding a migration”) that should be available to the model without being pasted into every request or kept in the project instructions permanently.
How to use it
Add .janetcode/skills/<name>/SKILL.md (or .md) in the project, or under the config directory for every project; run it directly as /<name> args, or let the model reach for it with its skill tool. /skills lists what is installed.

Memory

What it is
Facts and preferences kept across sessions as small markdown files, indexed by name and description in every request (cheap) and recalled in full only when a request clearly overlaps one (up to four per turn).
When it helps
A project convention or a personal preference (“I prefer small commits”) you are tired of repeating every session.
How to use it
The model's own memory tool records what a turn established; /remember [-g] <fact> adds one directly (-g for global, across every project), /memory lists them, and /forget <n> removes one.

A value that looks like a credential — an API key, a private key block, a JWT — is refused with an explanation: memory is written to disk and read back into every later prompt, which is the last place a secret belongs. Only you can write a global entry that applies to every project; anything the model extracts on its own stays scoped to the current one.

Path-scoped rules

What it is
A markdown file with a list of path globs in its frontmatter, sent to the model only once a tool call actually touches a matching path — unlike project instructions, which are sent on every request whether they are relevant or not.
When it helps
A rule that only matters for one corner of a large repository (“migrations are append-only”, scoped to db/migrations/**) that would be wasted context on every other request if it lived in the main project instructions.
How to use it
Add a file under .janetcode/rules/ with paths: in its frontmatter; /rules lists what is defined and which have fired this session.

Custom commands

What it is
A prompt template stored as a file, submitted as a slash command with your arguments substituted in.
When it helps
A request you type often, worded exactly the same way each time (“write a changelog entry for $ARGUMENTS in the style of …”).
How to use it
Add .janetcode/commands/<name>.md (project) or ~/.config/janetcode/commands/<name>.md (every project); run it as /<name> args, with $ARGUMENTS replaced in the template.

Repository map

What it is
A ranked map of which files and symbols in the repository matter for the current request, built by treating files as nodes and “file A uses a symbol file B defines” as an edge, then running the same kind of ranking web search engines use on links.
When it helps
Gives the model a sense of the codebase's shape without reading every file first, and answers “what would break if I changed this” without a full-project search.
How to use it
Attached automatically to every request; the model also has a repo_map tool to re-rank for another query or show a symbol's full blast radius (everything that defines or uses it).

By default it parses Go with the standard library's own parser and every other language with regular expressions, which cannot always tell a real declaration from the same words in a comment. Building with make build-treesitter compiles in real grammars for Python, JavaScript, TypeScript, Rust and C instead, at the cost of needing a C toolchain (cgo) — which is why it is opt-in rather than the default.

Interfaces

Web UI

What it is
The same session in a browser instead of the terminal: a three-column layout with the session list, a conversation column, and a tabbed panel for the plan, changed files, background jobs, subagents and this session's mode.
When it helps
You would rather click through permission prompts and tabs than use the terminal, or want to hand a colleague a link to watch a session (mind the warning below).
How to use it
janetcode --web; --web-addr to change the listen address.

The server binds to loopback (127.0.0.1:8787) unless you point it elsewhere. Anyone who can reach the port can approve commands in that directory, so treat the address the same way you would treat shell access to the project.

Editor integration (ACP)

What it is
Speaks the Agent Client Protocol on stdin and stdout, so an ACP editor can launch janetcode as a subprocess and drive it directly — sessions, streamed replies, tool calls and permission prompts all as protocol messages instead of terminal text.
When it helps
Running janetcode inside an editor that speaks ACP (Zed is the one it is tested against) instead of a separate terminal window.
How to use it
janetcode --acp, pointed at from the editor's own ACP agent configuration.

Headless and CLI use

What it is
Running one prompt to completion with no interactive terminal: assistant text on stdout, tool activity on stderr, and an exit code that says how it went — the shape a script or a CI job needs.
When it helps
Automating a task (“add a flag and open a PR”) from a script, or running janetcode as one step of a larger pipeline.
How to use it
janetcode -p "<prompt>" --yolo; add --output-format json for a single machine-readable result object, or stream-json for one JSON line per event as it happens. --until "<cmd>" keeps a headless run going until a command exits 0 (up to five rounds); the exit code is the verdict, never the model's own opinion of its work.

Without --yolo and without a terminal to ask, a mutating tool call is simply denied rather than left hanging — a headless run either has permission in advance or does not touch anything.

Cost and experience

Cost and budget

What it is
Running total of tokens and estimated cost for a session, and an optional hard ceiling that stops the session once it is reached.
When it helps
A long or exploratory session where you want to know what it is costing as you go, or a headless run in a script that should stop rather than run away.
How to use it
/usage (tokens and cost so far) and /stats (turns, model calls, tool calls per tool, failures, cache hit rate) inside a session; /budget <usd> to set a ceiling for this session, --max-cost <usd> for a headless run (exits 55 when reached).

A cost figure is labelled by where it came from: reported when the provider sent an actual figure with the response, list price when it was worked out from a rate table (an estimate, not money spent), and unpriced when neither is available.

Themes

What it is
A named colour palette for the terminal interface; eighteen are built in, from a historical default to Solarized, Nord, Dracula, Gruvbox, Catppuccin, a high-contrast theme and a near-colourless one.
When it helps
The default colours are hard to read on your terminal or background, or you simply prefer a different look.
How to use it
/theme opens a live, searchable list; /theme <name> switches directly; --theme <name> sets one for a single run. You can also define your own with fourteen named colour roles in the config file.

Hints

What it is
One-time, faint notices about a feature you appear not to know about, shown at the exact moment it would have helped — approving the same command a ninth time, or a command holding a turn open for twenty seconds with no mention of the key that would back it up.
When it helps
You are new to janetcode, or have never needed a particular corner of it; each hint fires at most once, ever, and never for a feature you already use.
How to use it
On by default; /hints off silences them for the session, "hints": false in the config file turns them off for good.

Step routing experimental

What it is
Sends a turn's purely mechanical steps — reading a file, listing a directory, re-running a check that already passed — to a second, cheaper model, while the first call of every turn, planning and edits stay on the main model.
When it helps
Nothing yet, by design: the manual is explicit that this should only be turned on after an eval run shows a real cost saving with no drop in pass rate on the harder task set, not from turning it on and reading a transcript.
How to use it
"route_cheap": "<model>" in the config file; empty (the default) is off. Measure it first with EVAL_ROUTE=<model> make eval, compared against a baseline — see the configuration reference and the evals manual for the exact commands.

Marked experimental deliberately: it is off by default, the policy is a short list of fixed rules rather than anything learned, and the project's own documentation says its value has to be demonstrated per project with an eval comparison before it is worth leaving on.

janetcode is a terminal coding agent. Source and issues: github.com/xmonader/janetcode. Drawn mainly from docs/manual/interface.md, with docs/manual/configuration.md, docs/manual/evals.md, docs/manual/sessions.md and docs/manual/editor.md.
