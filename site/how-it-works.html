How it works

One exchange with the model — from the moment you press enter to the moment janetcode is ready for your next message — is called a turn. Every turn follows the same loop.

The loop

  1. 1. You send a prompt. Typed at the terminal, given as a command-line argument, or piped in with -p for a one-shot, non-interactive (“headless”) run.
  2. 2. janetcode assembles the request. A ranked map of the repository (which files and symbols matter for this request), any project instructions (JANETCODE.md, AGENTS.md or CLAUDE.md), path-scoped rules that apply to files the request is likely to touch, recalled memory, matching skills, and pinned notes are added to the conversation before it goes to the model. See the repository map and memory.
  3. 3. The model replies. It streams markdown text and, when it wants to do something, structured tool calls: read a file, search the code, edit a file, run a shell command, and so on. Read-only tool calls (reading, listing, searching) run at once and concurrently; calls that change something run one at a time, in order.
  4. 4. A mutating call asks for approval. Editing or writing a file shows a diff; a shell command shows the exact command and, for destructive-looking ones (recursive deletes, force pushes, sudo, piping a download into a shell), a warning. You can allow it once, allow that tool for the rest of the session, deny it with a reason the model gets to read, or save a permission rule so the same shape of call never asks again. See permissions and modes, below.
  5. 5. The result goes back to the model. Tool output, and for code files any compiler or type errors a language server reports, are added to the conversation, and the loop returns to step 3. This repeats until the model has nothing further to do, or hits a limit (a model-call cap, a cost ceiling, a loop the harness notices and stops).
  6. 6. Verification gates run. If the turn changed anything and the project defines commands that must pass (a build, a test suite), they run now. A failure goes back to the model as another round of step 3-5, up to three times, before janetcode gives up and tells you.
  7. 7. janetcode computes a verdict. Not from what the model said, but from what was actually observed: did a check run and pass, did it pass only because the test itself was edited this turn, was nothing run at all. See verification and verdicts, below.
  8. 8. The turn is written to the session record. Every tool call, its result, the model's stated reason for each change, and the verdict are appended to a local, plain-text log. This is what /undo, /changes, /blame and /proof all read from later.

A turn that needs no tools at all — a question about the code — is the same loop with steps 4 through 7 simply having nothing to do.

Permissions and modes

janetcode has four modes, cycled with shift+tab or set with a flag: ask (the default: every edit and command asks first), plan (the model can only look, not change anything, until you approve a written plan), auto (in-workspace file edits and reads it already knows are safe run without asking; other commands still ask), and yolo (nothing asks; use this once you trust the task).

A few safety rules hold in every mode, including yolo: commands that would damage the machine itself (deleting / or the home directory, formatting a disk, a fork bomb, piping a download straight into a shell) are refused outright, and a command that reaches outside the working directory always asks, however the mode is set.

At a permission prompt, pressing r instead of y saves a rule so the same shape of call — the same tool, the same command pattern or path — never asks again in any session:

"permissions": {
  "allow": ["read_file", "bash(go test *)", "edit_file(internal/*)"],
  "deny":  ["bash(git push*)", "bash(rm -rf *)"]
}

/permissions lists and adds rules; a project can ship its own .janetcode/permissions.json, whose deny rules always apply and whose allow rules take a one-time /permissions trust before they do — the same caution that applies to anything a cloned repository asks to run automatically.

janetcode also keeps a private, per-project ledger of how you answered past prompts. It never saves a rule on its own; once a call's shape has been approved three times running with no refusal, the prompt itself notes that (“approved 4× before, never refused”) next to the rule that r would save, so the decision to stop asking is always one you make on purpose, just made easier to reach.

Sessions and undo

Every conversation is saved, append-only, to a local file. You can resume the newest one (--continue), resume a specific one by id (--resume <id>), or list what exists for the current directory (/resume inside the program). Long conversations are compacted: once the conversation grows past a size threshold, the old part is condensed into a short working-memory record instead of being sent in full on every request, and the full text of everything condensed is kept in a local archive that a tool called expand_output can search and page back through — so a detail lost from the summary is not lost from the disk.

/undo puts the working tree back to how it was before the last turn that changed anything, and removes that turn from what the model remembers too, so it cannot later refer to file contents that no longer exist. Inside a git repository this uses a hidden snapshot taken before the turn's first change, so shell-command edits and deletions revert along with tracked file edits; outside git, only the changes made through the file-editing tools are reversible. /undo about <description> is finer-grained: it previews which of the session's recorded changes match a description (“the logging changes but keep the rename”) and reverts only those, checking first whether undoing one change would break code a kept change still relies on.

Every change is also recorded with the model's stated reason for making it, which is what /changes (list them, grouped by turn and intent) and /blame <path> (which turn wrote which line) read. This record — which turn, and stated why, wrote a given line — is what janetcode calls provenance; when a session commits its work, the same evidence can be attached to the commit itself as a git note (see proof notes).

Verification gates and verdicts

A project can say what “done” means by listing commands in .janetcode/verify.json — typically a build and a test run. After any turn that changed something, those commands run; a failure is fed back to the model as another round of work, and a pass is shown as verified: ….

Passing a check is not the same as the change being good, which is why janetcode reports a verdict for every turn that changed code — a judgment about what was actually demonstrated, computed from what ran and what it returned, not from the model's own summary:

Verdicts and what they mean
VerdictWhat it means
verifiedtests ran and passed afterwards (and it says so when a failing check flipped to green)
self-checkedtests passed, but the tests themselves were edited in the same turn
not demonstrateda check passed without exercising anything, or code ran with nothing asserting the result
unverifiedcode was edited and nothing was run against it
check failedsomething ran and came back red
vacuousa check exited 0 having found no tests to run
tests writtenan acceptance-test writing turn wrote only test files, and they fail, as they should until the implementation exists

When the model's own answer claims something the turn does not show — “tests pass” when none ran — it is told once, with what was actually observed, and asked to run the check or say plainly that it did not. This behaviour was calibrated by replaying 97 real turns and checking each verdict by hand; the breakdown from that run (42% verified, 32% self-checked, 10% not demonstrated, 10% unverified, no false accusations) is in docs/benchmarks/compaction/FACTS.md.

Subagents

A subagent is a second conversation the main model starts with the task tool to do one bounded job in its own context: explore part of the codebase, fix one failing test, review a diff. It can run on the same model or a different, perhaps cheaper one, and several can run in parallel. Its work does not fill up the main conversation — only its final report comes back, unless you open its transcript yourself (/agents, or ctrl+t for a live overlay).

A subagent given edit: true gets the full tool set inside a throwaway worktree — a second checkout of the same repository, on its own branch, that git can create without disturbing your actual working directory — so it can edit files and run commands there without asking, and hands back a reviewable patch rather than having touched your real tree directly. The --worktree <branch> flag does the same thing for an entire session, not just a subagent, so two sessions can work on one repository at once.

Full detail, including custom named subagents and how a job is routed to another model: subagents and teams on the features page.
