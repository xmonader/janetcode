# janetcode site

A small, static, hand-written site for janetcode: plain HTML and one CSS
file, no build step, no framework, no external requests. It works from
`file://` and offline.

## Viewing it

Either open `index.html` directly in a browser, or serve the directory so
relative links behave exactly as they will once published:

```sh
cd site
python3 -m http.server
# then open http://localhost:8000/
```

## Pages

- `index.html` — what janetcode is, why, install, a 60-second quick start,
  and a features overview
- `features.html` — every notable feature explained in plain language
- `how-it-works.html` — the turn loop, permissions, sessions/undo, subagents
- `reference.html` — commands, flags, exit codes, tools, configuration keys,
  environment variables and project files

`css/style.css` is the only stylesheet, a dark-first developer-tool
theme (system sans for prose, system monospace for code and the
terminal) with a light variant via `prefers-color-scheme`. Two small,
dependency-free scripts: `js/theme.js` toggles and remembers a light/dark
choice in `localStorage` (the button in the header; the page still
follows the system preference until you use it), and `js/copy.js` adds a
"copy" button to code blocks (skipping the illustrative terminal session
on the home page, which isn't meant to be copied) and does nothing else.

## Keeping it in sync with the manual

This site is a plain-language rewrite of the project's own manual in
`../docs/manual/` plus `../README.md`, `../internal/slash/slash.go` (the
command table) and `../internal/feature/commands.go` (the "when it
helps" lines). It is not generated by a script, so a change to any of
those needs a matching edit here:

- A new or changed slash command (`internal/slash/slash.go`) or flag
  (`docs/manual/cli.md`) → update the tables in `reference.html`. The
  commands table was produced by parsing `slash.go`'s `Commands` slice and
  the flags table by parsing the flag table in `cli.md`; re-running the
  same extraction (a short Python script pulling out the `{Name, Args,
  Help}` literals, or the markdown table rows, and HTML-escaping them) is
  the fastest way to regenerate them after a change, but hand-editing the
  affected rows is fine for a small change.
- A new feature, or a change to what an existing one does → add or edit
  its entry in `features.html` (what it is / when it helps / how to use
  it), and check whether `index.html`'s "Features, in brief" list or
  `how-it-works.html`'s loop description needs a line too.
- A new configuration key (`docs/manual/configuration.md`) → add a row to
  the configuration table in `reference.html`.
- A benchmark claim → only ever cite a number that is in
  `../docs/benchmarks/`, and say what it measured and where it lives, the
  way the existing claims on `index.html` and `features.html` do. Do not
  round a number up, and do not drop the caution about run-to-run
  variance in `../docs/benchmarks/harnesses/session/REPORT.md`-style
  results.

There is no link checker wired into a build here (there is no build).
Before publishing a change, a quick manual check is enough: open each
page and click through its links, or run a small script against the four
files that checks every `href="*.html"` and `href="*.html#*"` resolves to
a real file and, for the fragment, a real `id` in it.
